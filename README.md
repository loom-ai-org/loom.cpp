# loom.cpp

A data-driven inference engine built on [`ggml`](https://github.com/ggml-org/ggml). Instead of hardcoding
a neural network's topology in C++ per model architecture, `loom-engine` parses a JSON graph-topology
definition — embedded as a string in the GGUF file's own metadata, alongside the weights it describes —
and builds the `ggml` compute graph from it at runtime. See [`SPECIFICATION.md`](SPECIFICATION.md) for the
full design rationale.

Target: small models for TTS, ASR, computer vision, and small LLMs.

- **Milestone 1** — a small decoder-only LLM (embedding → RoPE → self-attention with a KV cache →
  RMSNorm → SwiGLU FFN → autoregressive greedy decoding).
- **Milestone 2** — ASR/vision encoder primitives (`CONV_1D`/`CONV_2D`/`POOL_1D`/`POOL_2D`/`GELU`, plus
  non-causal self-attention via `ATTENTION`'s `kv_cache: false` mode), validated with generic
  conv-subsampled transformer encoders shaped like ViT/Zipformer — not faithful reproductions of either
  (see [`BACKLOG.md`](BACKLOG.md)).
- **Milestone 3** — TTS building blocks: `OdeStepper`, a flow-matching forward-Euler ODE integration
  driver that builds its graph once and genuinely reuses it across every integration step (see
  `BACKLOG.md` for the root-caused `ggml_gallocr` aliasing finding that makes this safe — every declared
  input must be rewritten every step, even ones that never logically change), and
  `CONV_TRANSPOSE_1D`/`CONV_TRANSPOSE_2D` for VAE-decoder-style upsampling. Validated with a generic conv
  vector-field network and a generic conv-transpose decoder — not a faithful reproduction of any
  published flow-matching/VAE architecture.

All three milestones are validated end-to-end against synthesized, deterministic toy GGUF fixtures — no
real model download needed, and the C++ output is checked against an independent numpy reference
implementation of the same forward pass.

## Building

Requires CMake 3.19+, a C++17 compiler, network access on first configure (`ggml` and `nlohmann/json`
are fetched via `FetchContent`), and Python 3 with `gguf` and `numpy` installed (`pip install gguf
numpy`) for the test suite's fixture generation.

```sh
cmake -B build
cmake --build build -j"$(nproc)"
ctest --test-dir build --output-on-failure
```

Try the CLI against the toy LLM fixture generated by the test suite (or `python3
tools/fixture_gen/make_toy_llm_gguf.py <path.gguf>` to make one standalone):

```sh
./build/tools/loom_cli/loom_cli --model build/tests/fixtures/toy_llm.gguf --prompt "1 2 3" --n-predict 8
```

There's no tokenizer yet, so `--prompt` takes whitespace-separated integer token ids rather than text.

## Layout

- `include/loom/`, `src/` — the engine library (`loom_engine`): GGUF/weight loading, the JSON graph
  schema, the primitive registry (JSON op name → `ggml` call), the graph builder (two-pass
  metadata/allocate strategy), the KV cache, the autoregressive generation driver, and the ODE-stepper
  driver.
- `tools/loom_cli` — a small CLI demo binary that loads a `.gguf` model and generates tokens.
- `tools/fixture_gen` — Python scripts (using `gguf-py` + `numpy`) that synthesize tiny seeded toy-model
  GGUF fixtures (LLM, vision encoder, ASR encoder, flow-matching vector field, VAE decoder) and compute
  their expected output, used by the test suite.
- `tests/` — the `ctest` suite: primitive registry, graph-topology parsing, graph-builder shape
  correctness, allocator reserve/reuse behavior, KV cache, `ggml` graph-reuse safety, and full load→run
  end-to-end tests for the LLM, both encoders, the ODE stepper, and the VAE decoder.

See [`BACKLOG.md`](BACKLOG.md) for deliberate scoping decisions and deferred work (performance
optimizations, single-sequence-only KV cache, what's left for a faithful ViT/Zipformer/flow-matching/VAE,
and an important finding about `ggml` graph-reuse safety).
